# 旅行规划 Agent：产品需求

状态：产品需求、基础技术栈与简化方案已确认。首轮使用西安验证，在 Windows（Intel／AMD）验收个人安装；下一阶段核对外部服务接入并实现端到端原型。

## 产品目标与首版范围

面向中文自由行用户，为目的地和日期已确定的 3–7 天休闲旅行，结合个人知识库和网络搜索生成可调整的行程。实际使用时由用户选择中国大陆的目的地城市，每次规划一个城市，覆盖景点、餐饮和当地交通。西安是首轮开发验证与验收的主要样本。

每个安装实例供一个人使用，在个人电脑安装并通过本机浏览器访问；资料、偏好与行程持久化在安装设备。通过 Docker Compose 启动单个应用容器，首个验收平台为 Windows（Intel／AMD）；详细方案见[技术栈选型](tech-stack.md)。

航班、住宿作为用户提供的已知条件参与规划；首版不搜索推荐航班或住宿，也不执行预订。产品入口为响应式网页，包含简表单、补充对话和可编辑的按天行程。

## 用户流程

1. 填写目的地、日期和同行人数，选填预算与补充说明；兴趣、限制和已知安排在同一输入框中自然表达。
2. 查看或编辑偏好档案，主动提供与旅行有关的资料。
3. 基础条件齐全后直接规划，景点组合、节奏和餐饮选择由 Agent 推荐。仅缺少必要信息或明确条件冲突时补充提问；模型一轮最多两个简短问题。问题在当前页面弹窗展示，回答追加到原行程并继续原任务；普通偏好可选择按推荐安排，明确限制仍需遵守。
4. Agent 检索个人资料、搜索地点和时效信息，生成并核验行程草案。
5. 用户查看按天的早、中、晚安排、交通与大致耗时，查看事实来源并修改行程。
6. 用户确认后，才将本次修改或反馈中提炼的新偏好写入长期档案。

景点与街区活动附由模型生成的简短介绍，内容为地点特色与可体验内容，不解释规划理由。餐饮默认只安排午餐、晚餐等大致时段，不指定店家；餐费作为估算，区域位置用于交通估算，不套用景点或某家餐馆的营业时间。

## 个性化规则

| 编号 | 已确认规则 |
| --- | --- |
| R01 | 本次明确要求优先于偏好档案，个人资料用于补充背景；推测偏好不作为硬约束。 |
| R02 | 先满足日期、预算等明确限制，再按本次重点排序，长期偏好作为辅助。旅行预算选填，以人民币表示全体同行者、整个行程的门票、餐饮和当地交通总额；填写后作为上限，费用缺失时标记待核实。 |
| R03 | 行程修改可以影响本次规划；长期偏好更新需要用户确认。 |
| R04 | 页面不解释推荐与个人偏好的匹配理由；事实依据仍展示来源和查询时间。 |
| R05 | 目的地、日期和人数为基础条件；普通偏好缺失时采用可见假设生成草案。仅必要缺口或明确条件冲突触发追问，不重复询问已提供或已回答的内容；不询问住宿档次或要求用户决定景点组合。预算口径与用户明确说明冲突时需澄清。 |

| R22 | 个人资料在本机提取文字、分段和建立关键词索引；规划时将相关片段与偏好提供给模型。 |

| R24 | 网页搜索默认按 Exa → DeepSeek → Tavily → AnySearch 顺序回退，取得可用来源后停止；无可用结果、限流或服务失败时尝试下一家，记录来源及失败原因。Exa 无 Key 时可使用官方匿名 MCP，全部失败时保留待核实状态。 |

## 首版效果

以“符合明确约束、事实依据可核对、用户只需少量修改就愿意采用”为核心目标，通过固定案例与个人实际试用共同验证。生成耗时与 API 调用费用不设目标或验收门槛；具体案例见[验收设计](acceptance.md)。

## 简化原则

资料处理、安装和维护尽量简单，复用 SQLite 做本地关键词检索，采用基础文字解析和手动备份，围绕西安行程跑通个人资料检索、网络搜索、生成、核验和编辑。具体实现与验证依据见[技术栈选型](tech-stack.md)。
